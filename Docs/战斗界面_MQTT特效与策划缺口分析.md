## 一、对上一版文档的修正

上一版（2026-11-26 早些时候）有以下不准确，已改正：

1. 「现状结论」里说没有场次运行时、HUD 只靠 `UwbHudMock` 假数据——已过时。`ScoreCardMatchRuntime` 已订阅 `ScoreCardCommandEvent`，写入 `UwbHudData` 和 `ScoreCardCombatState`，并向 3D 层发 `CombatCue`。
2. 「HUD 档位 UI 已有雏形，缺死亡灰卡/待复活」——已过时。10/20/40 三档底卡、头顶标牌、倒计时/待复活均已做完，但「灰」只有透明度降低，没有灰化（见 P13）。
3. 「特效表 BUFF 已接」——只对了一半。取得 BUFF 的瞬间会播一次 Redbuff/Bluebuff 预制体（2.5 秒后销毁），策划要求的是「持续到死亡 + 姓名旁 ICON」，目前都没有。
4. 「`VFX_UWB_2.5DView_BUFF_Heling` 回血特效已接」——当时代码里有 `NotifyHp` 对比血量回升的逻辑，但 `ScoreCardMatchRuntime` 所有路径都传 `playHpFx:false`，从未触发。2026-11-27 起 REFRESH_DATA 路径已打开（见 P20）。
5. 「积分模式 Mock 已接 BUFF/回血」——不准确。`ScoreCardScoreModeMock` 会发 S4/REFRESH_DATA、SHOOT(HIT/KILL)、MULTI_KILL、TOWER_KILL、PLAYER_REVIVE，但不发 RED/BLUE_BUFF_CAPTURED、FIRST_BLOOD，也没有回血。
6. 「P26–27 击杀流/高光 协议有，单屏 UI 未做」——结论没错，但还要补一条：MULTI_KILL/FIRST_BLOOD 会发出 MultiKill cue，`VenueCombatFxPlayer.HandleCue` 没有对应分支，所以现在既没有 UI 也没有特效。
7. 上一版只覆盖了 P10–P39 中和特效相关的部分，漏掉了全屏阶段（P2–P9）、双榜（P3–P6）、人物动作（P17）、地图机制（P23–P25）、音效（P37）、最后击杀回顾（P29–P32）、异常恢复（P33）。本版补全。

## 四、逐页核对

### P2 全屏阶段与结束流程 `[未做·待输入]`

- **策划**：双榜 → 赛前等待 → 开赛 5 秒 → 实时观战 → 最后击杀回顾 → 主舞台引导 → 双榜；新局优先打断。
- **现状**：没有阶段状态机。进入大厅后直接打开 `UwbGameHudPanel`；`ScoreCardMatchRuntime` 注释明确「不负责切屏页面」。
- **缺少**：`matchId`、`phase`、`startAt`、`endAt`（见 P34、[第九节](#九服务端缺失的消息与字段汇总给后端对接用)）。协议里有 `playStatus`（旧场次状态：备战/加载/竞拍/投点/购物/战斗/休息/结束/锁定），但与策划的阶段（等待/开赛 5 秒/进行/回顾/离场）不对应，UWB 客户端目前也没使用它。

### P3–P6 门店双榜（竞速榜、等级榜） `[未做·待输入]`

- **策划**：TOP50，前三固定、4–10 名固定、11–50 名每 8 秒换一组 7 人；5 分钟刷新；失败保留旧快照。

- **设计图**：已有（竞速排行榜.psd、等级排行榜.psd）。

对照 `ScoreCardSubCodeTester`、`ScoreCardMatchMockBuilder`、`ScoreCardKillstreakMock` 的写法：

- 信封：`msgType` / `msg{category, subCode, autoPlay, [serverTimestamp], data}`；只有 S4 整场快照带 `serverTimestamp`。
- S4 是 PAGE，**REFRESH_DATA 是 EVENT**（之前 Mock 误发成 PAGE，已改）。
- 首杀、连杀、BUFF 夺取按服务端真实顺序先发 NOTICE（只带 `name/vestId/id`，给语音用）再发 EVENT（带完整数据）。运行时只处理 EVENT，NOTICE 直接忽略，避免同一件事触发两次。
- 快照字段补齐为 ScoreCardUnity 的整套：`storeName`、`placeCode`、`playStatus`、队伍 `teamType`/`resultStatus`、玩家 `assistNum`、`topKillNum`、`initBullet`、`type`、`matchScore`、`killFriendNum`、`bullet`、`mvpType`、`gmtCreate`、`wxHeadImgUrl`；去掉 ScoreCardUnity 不发的 `initBlood`（血条分母沿用 100 的兜底值，Mock 满血也是 100）。
- TOWER_KILL.victim、PLAYER_REVIVE.player、BUFF_CAPTURED.killer 使用真服字段集（`matchScore`、`killNum`、`assistNum`、`name`、`beKillNum`、`vestId`、`id`、`blood`），炮杀同时累计死亡数。
- MULTI_KILL 补 `extraScore`（取 ScoreCardUnity 按服务端实测的数值）。
- 顺带修了 UWB 与 ScoreCardUnity 不一致的一处：`ApplyMultiKillEvent` 原来把 `comboCount` 写进 `killNum`，连杀后击杀数会被改成连杀数，现与 ScoreCardUnity 一致，只合并 shooter 带的字段。

### 没有

保护、护甲、阶段、`eventId`。

## 九、服务端缺失的消息与字段汇总（给后端对接用）

**组织方式**：按 UWB 版本要播放的动画/特效逐条对应（资产来源：`特效播放时机.xlsx` 的 12 个预制体 + 策划 P17/P35/P36 的动作与场地资产 + P7–P9、P29 的全屏演出）。每条写清楚：什么时候播、现在靠什么触发、需要哪些事件或字段、现有的类似事件为什么不能用。

**依据**：ScoreCardUWB 里的协议模型（`ScoreCardCommand`、`ScoreCardMatchData`、`ScoreCardPlayer` 及各事件 data 类）、ScoreCardUnity 里的旧协议（`MqttMessageType`、`SufferRecord`）。

> **注意**：「已有」只代表协议模型里有定义，服务端是否真的下发、多久下发一次，都没有联调验证。下文事件名是建议命名，后端可以改，关键是字段。

### 9.0 先看全局：所有条目共用的两个缺口

后面每一条几乎都会用到这两项，所以单独列出，条目里只引用编号。

**G1 事件公共头（所有事件都带）**

| 字段 | 含义 |
|------|------|
| `matchId` | 场次标识，识别旧局迟到事件 |
| `eventId` | 全局唯一，同一事件的 NOTICE 与 EVENT 共用，用于去重 |
| `eventSeq` | 同一 `matchId` 内单调递增，用于排序 |
| `eventTime` | 事件发生时刻，毫秒，服务器时钟 |
| `lastEventSeq`（放在 S4/REFRESH_DATA 里） | 这份快照已经包含到第几号事件，用于判断快照与事件谁新谁旧 |

现有情况：事件只带业务字段；`msg.serverTimestamp` 是消息发出时间，不是事件发生时间。后果：重复投递无法去重；快照比事件旧时无法识别；迟到的旧局事件无法识别；展示缓冲只能按「收到时刻 + 0.3 秒」算，网络抖动会变成画面抖动。

**G2 玩家身份映射**

玩家 `id` ↔ `vestId`（装备序号）↔ UWB tag uid 的权威绑定，S4 名册里带 `tagId` 或单独下发。UWB 客户端有 `UwbTagRegistry` 维护 uid → 玩家，但映射来源和下发时机没有确认。所有事件要对上人物位置，都依赖它。

### 9.1 角色战斗动画与特效

#### 9.1.1 受击特效 + 受击动作 + 护甲受击 `[无需后端；护甲/保护拒绝不做]`

- **资产**：`Attack_Behit01`、AN04 受击反应、CF02 护甲受击短闪。
- **做法**：沿用 `SHOOT`。`HIT` 与 `KILL` 都播 Behit01，致死再播 Dead。ScoreCardUnity 的比分牌通道只认 `scoreCard` 等几种 `msgType`，其余一律忽略，所以能收到的受击类消息只有 `SHOOT`、`TOWER_KILL`（致死，见 9.1.6）和竞速靶场的 `RANGE_BE_HIT`（只有音效，积分模式不发）。
- **不做的部分**：
  - 护甲吸收短闪、保护拒绝：`SHOOT` 里没有对应标记。
  - 受击部位（枪、头盔、背部）：只在 `sufferRecord` 里有。
  - `sufferRecord`、`attackRecord`、`armor`、`shield` 属于玩家端游戏连接，走玩家个人主题，比分牌通道收不到。
- **客户端工作**：受击动作 AN04 缺动画资产，和协议无关；S6-1 兵人动作清单里没有单次受击片段。

#### 9.1.2 死亡特效 + 灰化 + 死亡动作 `[无需后端]`

- **资产**：`Attack_Dead` + `MatDead.anim`、AN05 死亡动作、CF03 灰化。
- **做法**：
  1. 判死与 ScoreCardUnity 一致：`ScoreCardPlayer.IsDead() => blood == 0`（UWB 的同名方法已相同）。血量变成 0 的那一刻，立刻播死亡特效、死亡动作并灰化，之后保持灰态等复活。
  2. 复活倒计时取 `baseData.reviveCd`（`ScoreCardMatchData.reviveCd`），ScoreCardUnity 只在荣耀积分、攻防积分模式显示，其他模式不显示。倒计时只是展示，真正的「可以复活」由服务端控制。
  3. 灰态一直保持，直到收到 `PLAYER_REVIVE`，才播复活（见 9.1.3）。Mock 里「走回出生点再发复活」只是 Mock 的逻辑，真实比赛只以 `PLAYER_REVIVE` 为准。
- **触发来源**：`SHOOT`（`KILL`）、`TOWER_KILL` 的 `victim`、快照 `blood==0`。栅栏、毒圈、安全区致死也会让 `blood` 变成 0，所以不需要单独的消息。
- **关联**：`finishDeathsTime` 不用于判死。它的含义是「完全阵亡」时刻，用于排序和存活时长统计。

#### 9.1.3 复活特效 + 复活动作 + 保护外圈 `[复活脉冲无需后端；保护时长需补]`

- **资产**：`Attack_Reborn` + `MatReborn.anim`、AN06 复活动作、CF05 复活保护外圈。
- **策划时机**：服务端确认复活的瞬间播复活脉冲；复活后保护期内显示外圈，保护结束时外圈消失。
- **复活脉冲 + 复活动作**：只认 `PLAYER_REVIVE{player}`，在玩家当前的 UWB 位置播放，不需要复活点位置。灰态一直保持到收到该事件。Mock 里「回到出生点再发复活」只是 Mock 的逻辑，真实比赛不用。**现有消息足够**。
- **保护外圈**：ScoreCardUnity 的比分牌消息里没有任何保护时间字段（`ScoreCardPlayer`、`ScoreCardMatchData`、`PLAYER_REVIVE` 都没有）。只有旧版 HTTP 玩家模型里有一个未使用的私有字段 `invincibleEndTime`，不在比分牌通道里。
- **需要补的**：保护时长（秒）。策划文档写的是「保护结束时刻 `protectEndAt` 或本局配置」，选哪种由后端定；放在 `baseData`（和 `reviveCd` 同级）最简单，因为 `PLAYER_REVIVE` 的到达时刻就是起点。
- **补上之前**：客户端先用一个本地写死的保护时长做假外圈，真实值到位后替换。
- **关联缺口**：G1。

#### 9.1.4 回血特效 `[本地对比血量；回血不准，需与服务器协商]`

- **资产**：`BUFF_Heling`。
- **策划时机**：玩家血量回升的瞬间（蓝 BUFF 回复、复活点回复等）。
- **做法**：`REFRESH_DATA` 里某玩家血量比本地上一次高、且上一次大于 0，就播回血特效。新一局重置和 0 血回升（复活，由 `PLAYER_REVIVE` 负责）不算。
- **已知问题**：回血会不太准。快照若比某次命中事件更早生成，旧血量偏高会误报回血；两次快照之间先扣后补会漏报。需要与服务器协商修复，目前不提出具体字段。

#### 9.1.5 红/蓝 BUFF 持续特效 + 姓名旁 ICON `[沿用 ScoreCardUnity，无需新增]`

- **资产**：`BUFF_Redbuff`（CF06 红增伤光）、`BUFF_Bluebuff`（CF07 蓝回复环）、姓名旁 BUFF ICON、「获得增伤/回复」局部提示。
- **策划时机**：获得 BUFF 时开始播，持续到 BUFF 结束；死亡同帧清除；重连后按当前有效 BUFF 恢复。
- **ScoreCardUnity 有没有结束/到期时刻**：没有。消息里没有 BUFF 结束事件，也没有到期时间字段。ScoreCardUnity 用玩家的 `buffList`（字符串列表）：列表里有对应 BUFF，姓名旁图标就显示；下一次快照里没有了，图标就隐藏（`ScoreCardFightPlayerItem.ApplyBuffList`、`ScoreCardPlayerBuffType.HasRed/HasBlue`）。
- **UWB 的做法**：沿用同样的方式。
  1. `RED/BLUE_BUFF_CAPTURED` 到达时开始播特效。
  2. 以 `buffList` 是否仍含该 BUFF 作为持续和结束的依据，死亡同帧清除。
  3. `LOW_HP_BUFF`、`SAVIOR` 与红 BUFF 共用红色节点，和 ScoreCardUnity 一致。
  4. 重连后按当前 `buffList` 恢复。
- **待确认**：服务端是否在快照和事件里真的下发 `buffList`（见 9.5 第 2 条）。
- **关联缺口**：G1、G2。

#### 9.1.6 基地防御大炮：炮弹 + 受击特效 + 常驻状态 `[服务端将新增消息，字段待定]`

- **资产**：`Town_Bullet_Blue` / `Town_Bullet_Red`（蓝/红大炮子弹）、`Attack_Behit02`（受到蓝色大炮攻击）、`Attack_Behit02_Red`（受到红色大炮攻击）、MF06 基地防御攻击短闪、装置待机低亮。
- **策划时机**：防御装置攻击玩家时，炮弹飞向目标；命中时目标播对应颜色的炮击受击；装置待机时低亮，攻击时转向目标并短闪；击杀流显示「基地防御」。
- **现在靠什么触发**：`TOWER_KILL{victim}`。仅致死时，在大炮挂点播炮弹，受害者播 Behit02 并死亡。炮的颜色由「受害者队伍的对立队」推断。
- **服务端新增**：「被防御塔击中」的 MQTT 消息，类似 `SHOOT`（防御塔打中玩家就发，不只在致死时发）。**字段暂不确定**，等后端给出后再对接。客户端到时按这条消息播炮弹和炮击受击。
- **备注**：现在大炮挂点用 Mock 的固定坐标，真实场地需要标定后的挂点（场地数据，不是协议问题）。

### 9.2 场地机制

#### 9.2.1 复活点区域（MF05）

- **策划时机**：区域固定显示归属；待机 / 可用 / 复活成功扩散一次脉冲 / 封锁变灰。
- **现在靠什么触发**：没有场景表现。
- **需要的事件**：`RESPAWN_POINT_STATE`：`pointId`、`team`、`state`（待机 / 可用 / 封锁）、`eventTime`。
- **为什么类似功能不能用**：
  - 用玩家位置进入区域来推断「可用/复活」是观战端自行判定，和服务端装置识别的结果可能不一致；
  - 「封锁」状态没有任何字段能表达。
- **场地数据**（非协议）：区域多边形或中心点。
- **关联缺口**：G1。

#### 9.2.2 红/蓝 BUFF 靶灯争夺（MF01–MF04） `[字段待与服务器沟通]`

- **策划时机**：未刷新 / 可争夺 / 夺取中（结构条、F 交互短线）/ 夺取完成 / 脱战恢复；刷新时亮起，夺取时收束。
- **现在靠什么触发**：没有场景表现。现有的 `RED/BLUE_BUFF_REFRESH` 只是 NOTICE 语音，`RED/BLUE_BUFF_CAPTURED` 只代表夺取完成，其余状态没有数据。
- **需要的事件**：靶灯状态消息，字段需要和服务器沟通，客户端先不定。
- **场地数据**（非协议）：靶灯坐标。

### 9.3 全屏演出

#### 9.3.1 赛前等待

- **策划时机**：赛前地图顶部浮层「等待比赛开启」，顶栏「待开始」，角色灰模 + 队色菲涅尔（CF08），隐藏标牌与底卡。
- **现在靠什么触发**：没有，进大厅直接进入战斗 HUD。
- **需要的字段**：`phase`（等待 / 开赛倒数 / 进行 / 回顾 / 离场）；阶段起止时刻；撤销开赛、整局取消的信号。
- **为什么类似功能不能用**：
  - `playStatus`（`GameState`：备战中、加载中、竞拍中、投点中、购物中、战斗中、休息中、结束、锁定）是旧场次状态，不对应「等待开赛 → 开赛 5 秒 → 进行 → 回顾 → 离场」，也没有「等待比赛开启」这个阶段；
  - 客户端目前没有用到 `playStatus`，是否随 `data` 下发待确认。
- **关联缺口**：G1。

#### 9.3.2 开赛 5 秒三镜头与倒数

- **策划时机**：开赛窗口 5 秒，三镜头 1.5/1.5/2.0 秒，倒数 5→0 与镜头共用开赛时刻；中途接入按进度补位。
- **现在靠什么触发**：没有。
- **需要的字段**：`phase=开赛倒数` 与 `startAt`（服务端毫秒时刻），并确认 `msg.serverTimestamp` 每条消息都带，用来校准本机时钟。
- **为什么类似功能不能用**：
  - `BEGIN_PLAY`（S3 倒计时入口）可以当「开赛倒数开始」的近似信号，但它不带服务端时刻，客户端只能用「收到时刻」起算，网络延迟会直接变成倒数误差；
  - 中途接入（重连）时，没有开赛时刻就无法按进度补位；
  - ScoreCardUnity 的 S3 倒计时视频是 7 秒（`beginTimeOffsetSec = 7`），策划是 5 秒，两者对不上；UWB 客户端的剩余时间现在直接用 `startTime + matchDuration`，没有扣这 7 秒，要请后端确认 `beginTime` 之后到真正开打之间到底多长。
- **关联缺口**：G1。

#### 9.3.3 最后击杀回放

- **策划时机**：比赛结束后按 `lastKillEventId` 回放射击、弹道、命中死亡三分镜（约 6 秒）。
- **现在靠什么触发**：没有。
- **需要的事件**：结束事件带 `lastKillEventId` 和最终 `eventSeq`；所有击杀事件带 `eventTime`，才能和位置缓存对齐。
- **为什么类似功能不能用**：
  - S6 系列回顾页事件（S6_1/S6_2/S6_3）是切屏指令，不带最后一次击杀的标识；
  - SHOOT/TOWER_KILL 没有 `eventId`，也没有发生时刻，无法在位置缓存里找到对应帧；
  - 装置致死的击杀不应进入候选，需要 9.1.6 新增消息里能区分来源才能排除。
- **关联缺口**：G1。

#### 9.3.4 击杀流与高光（非动画，一并列出）

- **策划时机**：右上角最多 5 条，每条 6 秒；比分条下显示首杀、连杀高光。
- **现在靠什么触发**：协议已有 MULTI_KILL、FIRST_BLOOD，客户端解析后发出 cue，但没有 UI（`[暂缺设计图]`）。
- **需要补的**：`eventId`（去重、迟到 2 秒不补播）；击杀来源是玩家还是装置（见 9.1.6）。
- **为什么类似功能不能用**：用 `killNum`/`beKillNum` 增量可以勉强判断「有人击杀」，但拿不到击杀者对应关系和装置名，也无法去重；所以必须等 G1。

### 9.4 汇总：需要后端新增/增强的消息
